Por que "Untracked Files" e como funcionam as 3 Áreas?

Fundamental

Quando você inicializa com git init, os arquivos estão apenas no seu disco (Working Directory). O Git sabe que existem, mas não guarda versões até você mandar.

1. Working Directory Untracked / Modified (Vermelho)
➡️ git add ➡️
2. Staging Area (Index) Changes to be committed (Verde)
➡️ git commit ➡️
3. Repositório Commit salvo permanentemente
Comandos essenciais
# Ver arquivos não rastreados ou modificados
git status

# Preparar todos os arquivos para commit
git add .

# Gravar o commit no histórico
git commit -m "feat: minha mensagem de commit"
02

Criando, Renomeando e Comitando em Branches

Branches

Regra de ouro: Todo commit que você faz vai exclusivamente para a branch em que você está no momento (onde o HEAD aponta).

Gerenciamento de Branches
# Criar e mudar para nova branch (ex: alpha)
git switch -c alpha

# Renomear uma branch (ex: de alfa para beta)
git branch -m alfa beta

# Ver em qual branch você está e onde ela parou
git branch -v

# Alternar entre branches
git switch beta
git switch main
💡 Dica: Se você comitar na branch beta e voltar para a main com git switch main, os arquivos voltam instantaneamente para a versão da main. A alteração fica guardada em segurança na beta!
03

O Mistério do git reset: Por que o arquivo continuou lá?

Histórico & Reset

O que é o HEAD? HEAD não significa "início do projeto", significa: "Onde estou pisando agora" (o commit atual da branch).

Comando Histórico (HEAD) Staging (Área de Preparação) Arquivos Físicos no Disco
git reset --soft HEAD~1 ⏪ Volta 1 commit ✅ Mantém as alterações preparadas ✅ Mantém intacto no seu editor
git reset HEAD~1 (mixed) ⏪ Volta 1 commit 🧹 Limpa a Staging Area ✅ Mantém o código no editor (não preparado)
git reset --hard HEAD~1 ⏪ Volta 1 commit 🧹 Limpa a Staging Area ❌ Apaga as alterações físicas
⚠️ Por que o x.txt continuou quando usou reset --soft?
Porque o --soft desfez o commit no histórico, mas deixou o x.txt na Staging Area! Quando um novo commit foi feito em seguida, o x.txt entrou nele novamente. Para sumir com arquivos físicos indesejados, você precisa de git reset --hard <hash-sem-o-arquivo>.
04

Como voltar o código sem precisar de git reset?

Segurança

Em repositórios compartilhados ou quando você quer segurança sem risco de perder código, use estas 3 ferramentas:

1. git revert (Padrão ouro em equipes)
# Cria um novo commit que anula exatamente as mudanças do commit atual
git revert HEAD
2. git restore --source (Restaura arquivos de um commit antigo)
# Restaura TODOS os arquivos para como estavam no commit c15d5ab
git restore --source=c15d5ab .

# Ou restaura apenas um arquivo específico
git restore --source=c15d5ab index.html
3. git checkout <hash> (Máquina do tempo temporária)
# Espia o projeto no commit antigo sem alterar histórico
git checkout c15d5ab

# Retorna para o presente na sua branch
git switch main
05

Passar Commits entre Branches (Cherry-Pick) & Deletar

Avançado

Quando você quer pescar apenas um commit específico de outra branch sem precisar fazer merge de tudo:

git cherry-pick 🍒
# 1. Veja o hash do commit na branch de origem
git log --oneline

# 2. Vá para a branch onde você quer aplicar o commit
git switch beta

# 3. Copie o commit para a branch atual
git cherry-pick 00d04ae
Deletar commits no meio do histórico (Rebase Interativo)
# Abre lista dos últimos 3 commits para editar
git rebase -i HEAD~3
# Na tela, troque 'pick' por 'drop' no commit que deseja apagar!

Conectando ao GitHub & Checando o Repositório

GitHub & Remotos

Como verificar onde seu código está indo e evitar o erro comum git: 'remove' is not a git command (é remote!).

Comandos de Conexão com GitHub
# 1. Checar se já existe um repositório remoto configurado
git remote -v

# 2. Conectar ao repositório do GitHub (cuidado: remote, não remove!)
git remote add origin https://github.com/Kevin-Pro-Codes/git-hub-sample.git

# 3. Renomear branch principal para 'main'
git branch -M main

# 4. Enviar os commits pela primeira vez
git push -u origin main

# 5. Baixar atualizações do GitHub
git pull origin main

Tutorial de Labels & Conventional Commits (Padrão Profissional)

Boas Práticas

O Conventional Commits é o padrão global da indústria para nomear commits de forma padronizada, legível por humanos e por robôs (geração automática de changelogs e versões semânticas).

tipo feat, fix, docs...
+
(escopo opcional) (auth), (ui), (api)...
+ :
descrição curta imperativo, sem ponto final
Label / Tipo Quando Usar? Exemplo Prático
feat: Nova funcionalidade para o usuário final feat: adiciona filtro por tarefas concluidas
fix: Correção de bug ou comportamento incorreto fix: corrige erro ao excluir tarefa com enter
docs: Apenas documentação (README, manuais, comentários) docs: atualiza instrucoes de instalacao no README
style: Apenas formatação, espaçamento, ponto e vírgula (sem mexer em lógica) style: formata indentacao no style.css
refactor: Refatoração de código (não cria feature nem conserta bug) refactor: simplifica funcao de renderizacao da lista
perf: Mudança que melhora o desempenho ou velocidade perf: otimiza loop de busca de tarefas
test: Adição ou ajuste de testes automatizados test: cria testes unitarios para criacao de tarefas
chore: Tarefas de manutenção geral, configs, dependências chore: adiciona arquivo .gitignore
build: Alterações em scripts de build ou dependências externas build: atualiza versao de pacotes no package.json
ci: Alterações em pipelines de CI/CD ou GitHub Actions ci: adiciona pipeline de deploy automatico
Exemplos com Escopo & Breaking Change
# 1. Com escopo (indica a parte específica do sistema afetada):
git commit -m "feat(ui): adiciona botao de alternar modo escuro"
git commit -m "fix(login): resolve falha na validacao de senha"

# 2. Breaking Change (mudança que quebra compatibilidade com versões antigas, usa '!'):
git commit -m "feat(api)!: remove endpoint /v1/tasks legado"

# 3. Commit com corpo explicativo longo:
git commit -m "fix(storage): evita perda de dados ao fechar aba" -m "Agora as tarefas sao salvas no localStorage antes do evento beforeunload."
💡 Regras de Ouro para uma boa mensagem:
  • Use verbos no imperativo: "adiciona", "corrige", "remove" (em vez de "adicionado" ou "adicionando").
  • Mantenha a primeira letra minúscula após o tipo: feat: adiciona....
  • Nunca coloque ponto final no fim da primeira linha do commit.
  • Limite o título a no máximo 50 a 72 caracteres para não truncar no GitHub.

Tags no Git: Criando Releases, Versões e Versionamento Semântico

Releases & Versões

Uma Tag é um "carimbo fixo" (bookmark) em um commit específico. Enquanto as branches se movem a cada novo commit, uma tag nunca sai do lugar. É o padrão oficial para marcar versões e releases (ex: v1.0.0).

Tag Leve (Lightweight) Apenas um apelido para o commit: git tag v1.0.0
vs
Tag Anotada (Annotated - Recomendada) Guarda autor, data, e-mail e mensagem: git tag -a v1.0.0 -m "..."
1. Criando e Listando Tags Locais
# Criar tag anotada no commit atual (Recomendado):
git tag -a v1.0.0 -m "Release da versao 1.0.0 pronta para producao"

# Criar tag em um commit antigo do passado (basta passar o hash):
git tag -a v0.9.0 c15d5ab -m "Versao beta inicial"

# Listar todas as tags do projeto:
git tag

# Ver detalhes completos de uma tag (quem criou, data e mensagem):
git show v1.0.0
2. Enviando Tags para o GitHub (Push)
# ⚠️ ATENÇÃO: 'git push' normal NÃO envia tags!
# Para enviar UMA tag específica para o GitHub:
git push origin v1.0.0

# Para enviar TODAS as tags locais de uma vez para o GitHub:
git push origin --tags

# O GitHub automaticamente cria uma página de 'Release' para você!
3. Deletando Tags (Local e Remoto)
# Deletar uma tag localmente:
git tag -d v1.0.0

# Deletar a tag lá no GitHub (remoto):
git push --delete origin v1.0.0
Versionamento Semântico (SemVer) Formato: vMAJOR.MINOR.PATCH Quando Incrementar?
MAJOR (v2.0.0) Quebra de compatibilidade Mudanças drásticas que quebram o código ou API existente.
MINOR (v1.1.0) Nova funcionalidade Adiciona nova feature de forma compatível com a versão anterior.
PATCH (v1.0.1) Correção de bug Pequenas correções e consertos de bugs sem novas funcionalidades.
💡 Dica Prática: Se você rodar git checkout v1.0.0, o Git coloca você exatamente no código daquela versão (em modo Detached HEAD), permitindo testar ou compilar o sistema exatamente como ele foi lançado no passado!

Pull Requests (PR), Git Fetch & Colaboração em Equipe

Fluxo Profissional

Um Pull Request (PR) é o coração do trabalho em equipe e do código aberto. Ele permite que desenvolvedores proponham alterações de uma branch para a main, abrindo espaço para Code Review e testes antes do código ser mesclado.

git fetch Baixa dados da nuvem SEM alterar arquivos
+
git merge Junta as alterações na sua branch
=
git pull Fetch + Merge automático em 1 comando
1. O Segredo do Git Fetch (Espiar antes de misturar)
# 1. Baixa todas as branches e commits do GitHub sem mexer nos seus arquivos:
git fetch

# 2. Veja os commits que a nuvem tem que você ainda não tem:
git log HEAD..origin/main --oneline

# 3. Veja exatamente as linhas de código que foram alteradas na nuvem:
git diff HEAD..origin/main

# 4. Se estiver tudo seguro, aplique as novidades na sua branch:
git merge origin/main
2. Ciclo Completo de um Pull Request no GitHub
# 1. Crie uma branch específica para a funcionalidade:
git switch -c feature/nova-tarefa

# 2. Faça suas edições e commite:
git add .
git commit -m "feat(ui): implementa nova funcionalidade"

# 3. Envie a branch para o GitHub criando o rastreamento (-u):
git push -u origin feature/nova-tarefa

# 4. No GitHub: clique em 'Compare & pull request' e depois 'Create pull request'.
# 5. Após revisão da equipe, clique em 'Merge pull request'.

# 6. No seu computador, volte para a main e atualize tudo:
git switch main
git pull
3. Simulando 2 Desenvolvedores no mesmo computador (Truque do Collab)
# Clone o mesmo repositório em uma pasta paralela:
git clone https://github.com/Kevin-Pro-Codes/git-hub-sample.git DevColega

# Agora trabalhe na pasta DevColega como se fosse seu colega:
cd DevColega
# (edite arquivos, comite e dê git push)

# Depois volte para a sua pasta principal e puxe as alterações:
cd ../GitSample
git pull
💡 Por que usar Pull Requests em vez de commitar direto na main?
  • Protege a produção: Evita que código com bugs ou quebrado entre na branch principal.
  • Revisão de Código (Code Review): Outros desenvolvedores podem sugerir melhorias antes do merge.
  • CI/CD Automatizado: O GitHub Actions pode rodar testes automatizados e verificar se o build passou antes de permitir o merge.

Anatomia do Conflito: O que cada linha significa?

<<<<<<< HEAD (Current Change)

O código da branch onde você está no momento (geralmente a sua main ou test).

======= (Divisor)

A linha divisória exata que o Git coloca para separar as duas versões divergentes.

>>>>>>> origin/collab (Incoming Change)

O código novo que está tentando entrar através do Pull Request ou comando merge.

🚨 O Botão de Pânico (Cancelar tudo):
Se você encontrar dezenas de conflitos e quiser cancelar imediatamente sem quebrar nada: git merge --abort Ele restaura todos os seus arquivos exatamente ao estado antes de você tentar o merge!
